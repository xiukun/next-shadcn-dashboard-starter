# data-grid 规范（增量）

## 目的
本规范定义了企业级数据表格的能力要求，包括查询协议、列配置、编辑提交与验证等。

## 新增需求

### 需求：结构化验证支持

系统必须支持基于 Zod Schema 的结构化验证，同时保持与现有 `validate` 函数的向后兼容。

#### 场景：列级 Zod Schema 验证
- **当** 开发者在列配置中提供 `meta.zodSchema` 时
- **那么** 表格必须使用该 Zod Schema 进行验证
- **并且** 如果验证失败，必须返回结构化的错误信息（字段路径 -> 错误消息）

#### 场景：行级 Zod Schema 验证
- **当** 开发者通过 `createRowSchema(columns)` 生成行级 Schema 时
- **那么** 表格必须能够验证整行数据
- **并且** 支持跨列验证（例如：总价 = 单价 × 数量）

#### 场景：向后兼容旧的 validate 函数
- **当** 列配置中只有 `meta.validate` 函数而没有 `meta.zodSchema` 时
- **那么** 表格必须继续使用旧的 `validate` 函数进行验证
- **并且** 两种验证方式可以共存（优先使用 Zod Schema，如果没有则使用 validate 函数）

### 需求：灵活的编辑提交模式

系统必须支持三种编辑提交模式，以满足不同的业务场景需求。

#### 场景：即时提交模式（默认）
- **当** `DataGrid` 的 `editMode` 属性为 `'immediate'` 或未设置时
- **那么** 用户编辑单元格后，按下 Enter 键应立即提交到后端
- **并且** 行为与现有实现保持一致，确保向后兼容

#### 场景：单行提交模式
- **当** `DataGrid` 的 `editMode` 属性为 `'single-row'` 时
- **那么** 用户编辑一行中的多个单元格后，编辑内容应暂存在编辑队列中
- **并且** 用户点击该行的"提交"按钮时，才将整行编辑提交到后端
- **并且** 在提交前，必须验证该行的所有编辑内容

#### 场景：批量提交模式
- **当** `DataGrid` 的 `editMode` 属性为 `'batch'` 时
- **那么** 用户编辑多行后，所有编辑内容应暂存在编辑队列中
- **并且** 用户点击"提交全部"按钮时，才将所有待提交的行批量提交到后端
- **并且** 在提交前，必须验证所有待提交的行
- **并且** 如果部分行验证失败，应显示错误信息，但允许提交验证通过的行（可选）

### 需求：编辑队列管理

系统必须维护一个编辑队列，用于暂存待提交的编辑内容。

#### 场景：编辑加入队列
- **当** 用户在非即时提交模式下编辑单元格时
- **那么** 编辑内容应自动加入编辑队列（`pendingEdits`）
- **并且** 如果同一行的同一单元格被多次编辑，应更新队列中的对应记录，而不是创建新记录

#### 场景：从队列移除
- **当** 用户取消编辑或提交成功后
- **那么** 对应的编辑记录应从队列中移除
- **并且** 如果用户点击"取消"按钮，应清空所有待提交的编辑

#### 场景：队列大小限制
- **当** 编辑队列中的记录数超过最大限制（例如 1000 条）时
- **那么** 系统应自动移除最旧的编辑记录
- **并且** 应向用户提示队列已满（可选）

### 需求：提交状态管理

系统必须跟踪提交状态，包括提交中、成功、失败等状态。

#### 场景：提交状态显示
- **当** 用户触发提交操作时
- **那么** 系统应将提交状态设置为 `'submitting'`
- **并且** 在提交过程中，应禁用提交按钮，显示"提交中..."提示
- **并且** 提交成功后，应将状态设置为 `'success'`，并显示成功提示
- **并且** 提交失败后，应将状态设置为 `'error'`，并显示错误信息

#### 场景：部分提交失败处理
- **当** 批量提交时，部分行提交失败
- **那么** 系统应记录失败的行和错误信息
- **并且** 成功提交的行应从队列中移除
- **并且** 失败的行应保留在队列中，允许用户重试

### 需求：性能优化

系统必须在大数据量场景下保持良好的性能表现。

#### 场景：防抖优化
- **当** 用户快速输入编辑内容时
- **那么** 草稿值的更新应使用防抖（例如 150ms）
- **并且** 避免频繁的状态更新导致性能问题

#### 场景：节流优化
- **当** 用户输入过程中需要实时验证时
- **那么** 验证操作应使用节流（例如 300ms）
- **并且** 避免频繁的验证计算导致性能问题

#### 场景：虚拟化优化
- **当** 表格使用虚拟化渲染时
- **那么** 验证操作应只针对可见行的编辑
- **并且** 不可见行的编辑应在滚动到可见区域时再进行验证

### 需求：状态解耦

系统必须将编辑状态与 UI 组件解耦，提升可测试性和可维护性。

#### 场景：状态分层
- **当** 系统管理编辑状态时
- **那么** 应将状态分为三层：
  1. **UI 状态**：当前编辑的单元格、草稿值（在组件中）
  2. **编辑队列**：待提交的编辑记录（在 store 中）
  3. **提交状态**：提交中、成功、失败（在 store 中）

#### 场景：逻辑复用
- **当** 需要在不同组件中使用相同的编辑逻辑时
- **那么** 应通过 Hook（如 `useTableSubmission`）提供可复用的逻辑
- **并且** 编辑逻辑应独立于 UI 组件，易于单元测试
