## 需求
### 需求：通用数据表格内核
系统必须提供一个与 UI 框架无关的通用数据表格内核，用于在多个前端项目中复用统一的数据查询协议、列配置模型和插件机制。

#### 场景：定义查询与结果协议
- **当** 任一前端项目需要展示支持排序、过滤、分页与分组的数据表格时
- **那么** 必须能够使用统一的 `DataGridQuery` 结构描述排序、过滤、分页与分组条件
- **并且** 后端返回的数据必须能够映射到统一的 `DataGridResult` 结构，以便多个项目共享相同的数据访问层实现

#### 场景：列配置模型可复用
- **当** 不同项目需要对相同领域实体（例如产品、用户、订单）构建表格列时
- **那么** 必须能够通过统一的 `ColumnConfig` 与 `ColumnMeta` 模型描述列 id、标题、访问器与元数据（类型、可编辑性、权限等）
- **并且** 相同的列配置可以在不同项目中直接复用，而无需依赖具体 UI 组件库

### 需求：React 表格绑定层
系统必须提供一个基于 React 的表格绑定层，将通用内核与 TanStack React Table、Zustand 状态管理和虚拟化渲染集成在一起。

#### 场景：通过 Hook 获取表格实例
- **当** 前端项目在 React 组件中使用数据表格时
- **那么** 必须能够通过 `useDataGrid` Hook 获取包含表格状态、行数据、列配置与常用交互处理函数的表格实例
- **并且** 该 Hook 内部必须使用通用内核定义的协议与控制器，而不是在业务组件中直接操作 TanStack Table 的底层细节

#### 场景：支持多表实例与状态隔离
- **当** 页面上存在多个数据表格实例或同一数据表格在多个页面/组件中复用时
- **那么** 每个数据表格实例必须有独立的状态存储（例如每个表一个 Zustand store）
- **并且** 必须能够通过唯一的 `gridId` 在需要时共享或恢复表格视图状态（例如列布局、排序与过滤配置）

### 需求：Next.js 数据源适配
系统必须提供一个针对 Next.js App Router 的数据源适配层，简化数据表格与后端 API 之间的交互。

#### 场景：通过统一适配器访问 Next API
- **当** 表格数据来自 Next.js 的 API Route 或后端服务时
- **那么** 必须能够通过 `createNextDataSource`（或等价 API）将 `DataGridQuery` 序列化并发送到指定端点
- **并且** 响应数据必须能够直接映射为 `DataGridResult`，供表格内核与 React 层使用

### 需求：多项目复用与性能
系统必须支持在多个项目中复用相同的表格内核与 React 绑定层，并在万行数据规模下保持可接受的性能体验。

#### 场景：多项目依赖同一 @maita-table 包
- **当** 不同前端项目通过包管理工具安装 `@maita-table/*` 依赖时
- **那么** 它们必须能够使用相同版本的查询协议、列模型与 React 表格组件，而无需复制粘贴实现
- **并且** 任一项目中的增强（例如新增列类型或插件）可以在不破坏公共 API 的情况下发布为新版本并被其他项目升级使用

#### 场景：万行数据下流畅滚动
- **当** 表格需要展示万行级数据（可以通过分页或无限滚动方式获取）时
- **那么** React 表格绑定层必须支持基于虚拟化的行渲染，避免一次性渲染全部 DOM 行
- **并且** 对排序、过滤与分页的变更必须通过统一的查询协议推到数据源层处理，而不是在前端对全量数据进行计算

### 需求：单元格编辑与内联表单
系统必须在现有数据表格内核的基础上，提供可复用的单元格/行编辑能力，包括编辑状态管理、基础校验与与后端 API 的交互约定。

#### 场景：列元数据声明可编辑性
- **当** 开发者在列配置中为某一列设置 `meta.editable: true` 时
- **那么** 表格必须在渲染该列时提供进入编辑模式的交互入口（例如点击单元格或双击）
- **并且** 必须可以通过 `meta.editorType` 指定编辑器类型（如 `text`、`number`、`select`、`checkbox`、`date` 等）

#### 场景：编辑状态与键盘交互
- **当** 用户在表格中将焦点移动到某个可编辑单元格并触发编辑（例如按下 Enter 或双击）
- **那么** 表格必须将该单元格标记为“编辑中”状态，并在前端状态中记录当前编辑的行 key、列 id 与暂存值
- **并且** 用户按下 Enter 时应提交当前单元格的暂存值，按下 Esc 时应取消编辑并恢复原值

#### 场景：本地校验与错误提示
- **当** 列的 `meta.validate` 函数返回错误消息时
- **那么** 表格必须阻止该单元格编辑的提交，并在 UI 中显式展示错误提示（例如在单元格下方或使用 red 边框与 tooltip）
- **并且** 错误信息必须能够通过统一的数据结构（例如 `validationErrors[rowKey:colId]`）被外部逻辑访问

#### 场景：数值范围与小数精度约束
- **当** 数值列在 `meta` 中配置了 `min`、`max` 或 `decimals` 时
- **那么** 用户在编辑该单元格时可以输入中间态（例如 `0.`、`-` 等），不会被立即转换为 `NaN`
- **并且** 在用户提交编辑（例如按下 Enter）时，系统必须：
  - 尝试将输入解析为数值；若解析失败，则回退为原值；
  - 应用 `min`/`max` 约束将值裁剪到允许范围内；
  - 根据 `decimals` 将值格式化到指定小数位（例如 `decimals: 2` 时最终显示为两位小数）。

#### 场景：数值显示格式与条件着色
- **当** 数值列在 `meta` 中配置了 `locale`、`thousandSeparator`、`formatStyle` 或 `currency` 时
- **那么** 表格在显示该列时必须使用本地化规则进行格式化（例如千分位分组、本地化小数点、货币符号和百分比）
- **并且** 当 `meta.colorBySign: true` 时，正数应使用正向颜色样式（例如绿色），负数应使用负向颜色样式（例如红色），具体 className 可通过 `positiveClassName` 与 `negativeClassName` 定制

#### 场景：与后端 API 的编辑提交流程
- **当** 用户提交对某一行或多个单元格的编辑时
- **那么** 表格必须能够通过已配置的数据源或回调触发一次后端 API 请求（例如 PATCH `/api/...`）
- **并且** 在请求成功时更新行数据，在请求失败时恢复原值并展示错误信息（允许选择乐观更新或悲观更新策略）
