# data-grid 规范

## 目的
本规范定义数据表格（DataGrid）在企业级场景下的核心能力边界与可验收行为，包括统一的查询/结果协议、可复用的列配置模型、React 绑定层与数据源适配、虚拟化性能要求，以及单元格编辑、结构化验证与编辑提交等交互约定。
## 需求
### 需求：通用数据表格内核
系统必须提供一个与 UI 框架无关的通用数据表格内核，用于在多个前端项目中复用统一的数据查询协议、列配置模型和插件机制。

#### 场景：定义查询与结果协议
- **当** 任一前端项目需要展示支持排序、过滤、分页与分组的数据表格时
- **那么** 必须能够使用统一的 `DataGridQuery` 结构描述排序、过滤、分页与分组条件
- **并且** 后端返回的数据必须能够映射到统一的 `DataGridResult` 结构，以便多个项目共享相同的数据访问层实现

#### 场景：列配置模型可复用
- **当** 不同项目需要对相同领域实体（例如产品、用户、订单）构建表格列时
- **那么** 必须能够通过统一的 `ColumnConfig` 与 `ColumnMeta` 模型描述列 id、标题、访问器与元数据（类型、可编辑性、权限等）
- **并且** 相同的列配置可以在不同项目中直接复用，而无需依赖具体 UI 组件库

### 需求：React 表格绑定层
系统必须提供一个基于 React 的表格绑定层，将通用内核与 TanStack React Table、Zustand 状态管理和虚拟化渲染集成在一起。

#### 场景：通过 Hook 获取表格实例
- **当** 前端项目在 React 组件中使用数据表格时
- **那么** 必须能够通过 `useDataGrid` Hook 获取包含表格状态、行数据、列配置与常用交互处理函数的表格实例
- **并且** 该 Hook 内部必须使用通用内核定义的协议与控制器，而不是在业务组件中直接操作 TanStack Table 的底层细节

#### 场景：支持多表实例与状态隔离
- **当** 页面上存在多个数据表格实例或同一数据表格在多个页面/组件中复用时
- **那么** 每个数据表格实例必须有独立的状态存储（例如每个表一个 Zustand store）
- **并且** 必须能够通过唯一的 `gridId` 在需要时共享或恢复表格视图状态（例如列布局、排序与过滤配置）

### 需求：Next.js 数据源适配
系统必须提供一个针对 Next.js App Router 的数据源适配层，简化数据表格与后端 API 之间的交互。

#### 场景：通过统一适配器访问 Next API
- **当** 表格数据来自 Next.js 的 API Route 或后端服务时
- **那么** 必须能够通过 `createNextDataSource`（或等价 API）将 `DataGridQuery` 序列化并发送到指定端点
- **并且** 响应数据必须能够直接映射为 `DataGridResult`，供表格内核与 React 层使用

### 需求：多项目复用与性能
系统必须支持在多个项目中复用相同的表格内核与 React 绑定层，并在万行数据规模下保持可接受的性能体验。

#### 场景：多项目依赖同一 @maita-table 包
- **当** 不同前端项目通过包管理工具安装 `@maita-table/*` 依赖时
- **那么** 它们必须能够使用相同版本的查询协议、列模型与 React 表格组件，而无需复制粘贴实现
- **并且** 任一项目中的增强（例如新增列类型或插件）可以在不破坏公共 API 的情况下发布为新版本并被其他项目升级使用

#### 场景：万行数据下流畅滚动
- **当** 表格需要展示万行级数据（可以通过分页或无限滚动方式获取）时
- **那么** React 表格绑定层必须支持基于虚拟化的行渲染，避免一次性渲染全部 DOM 行
- **并且** 对排序、过滤与分页的变更必须通过统一的查询协议推到数据源层处理，而不是在前端对全量数据进行计算

### 需求：单元格编辑与内联表单
系统必须在现有数据表格内核的基础上，提供可复用的单元格/行编辑能力，包括编辑状态管理、基础校验与与后端 API 的交互约定。

#### 场景：列元数据声明可编辑性
- **当** 开发者在列配置中为某一列设置 `meta.editable: true` 时
- **那么** 表格必须在渲染该列时提供进入编辑模式的交互入口（例如点击单元格或双击）
- **并且** 必须可以通过 `meta.editorType` 指定编辑器类型（如 `text`、`number`、`select`、`checkbox`、`date` 等）

#### 场景：编辑状态与键盘交互
- **当** 用户在表格中将焦点移动到某个可编辑单元格并触发编辑（例如按下 Enter 或双击）
- **那么** 表格必须将该单元格标记为“编辑中”状态，并在前端状态中记录当前编辑的行 key、列 id 与暂存值
- **并且** 用户按下 Enter 时应提交当前单元格的暂存值，按下 Esc 时应取消编辑并恢复原值

#### 场景：本地校验与错误提示
- **当** 列的 `meta.validate` 函数返回错误消息时
- **那么** 表格必须阻止该单元格编辑的提交，并在 UI 中显式展示错误提示（例如在单元格下方或使用 red 边框与 tooltip）
- **并且** 错误信息必须能够通过统一的数据结构（例如 `validationErrors[rowKey:colId]`）被外部逻辑访问

#### 场景：数值范围与小数精度约束
- **当** 数值列在 `meta` 中配置了 `min`、`max` 或 `decimals` 时
- **那么** 用户在编辑该单元格时可以输入中间态（例如 `0.`、`-` 等），不会被立即转换为 `NaN`
- **并且** 在用户提交编辑（例如按下 Enter）时，系统必须：
  - 尝试将输入解析为数值；若解析失败，则回退为原值；
  - 应用 `min`/`max` 约束将值裁剪到允许范围内；
  - 根据 `decimals` 将值格式化到指定小数位（例如 `decimals: 2` 时最终显示为两位小数）。

#### 场景：数值显示格式与条件着色
- **当** 数值列在 `meta` 中配置了 `locale`、`thousandSeparator`、`formatStyle` 或 `currency` 时
- **那么** 表格在显示该列时必须使用本地化规则进行格式化（例如千分位分组、本地化小数点、货币符号和百分比）
- **并且** 当 `meta.colorBySign: true` 时，正数应使用正向颜色样式（例如绿色），负数应使用负向颜色样式（例如红色），具体 className 可通过 `positiveClassName` 与 `negativeClassName` 定制

#### 场景：与后端 API 的编辑提交流程
- **当** 用户提交对某一行或多个单元格的编辑时
- **那么** 表格必须能够通过已配置的数据源或回调触发一次后端 API 请求（例如 PATCH `/api/...`）
- **并且** 在请求成功时更新行数据，在请求失败时恢复原值并展示错误信息（允许选择乐观更新或悲观更新策略）

### 需求：结构化验证支持

系统必须仅通过 Zod Schema 执行结构化验证，不再支持旧的 `meta.validate` 函数或任意返回字符串的自定义校验函数；所有列级与行级校验行为都必须可由 Zod 类型系统精确描述，并产出结构化的错误信息以供 UI 与提交逻辑复用。

#### 场景：列级 Zod Schema 验证（Zod-only）
- **当** 开发者在列配置中提供 `meta.zodSchema` 或通过辅助函数生成列级 Zod Schema 时
- **那么** 表格必须使用该 Zod Schema 作为该列的**唯一**结构化校验来源
- **并且** 如果验证失败，必须返回结构化的错误信息（字段路径 -> 错误消息），而不是仅返回自由格式字符串

#### 场景：行级 Zod Schema 验证
- **当** 开发者通过 `createRowSchema(columns)`（或等价 API）基于列配置生成行级 Zod Schema 时
- **那么** 表格必须能够在提交前对整行数据执行行级校验
- **并且** 必须支持跨列验证（例如：总价 = 单价 × 数量）、必填字段组合约束等复杂规则

#### 场景：不再接受旧的 validate 函数
- **当** 列配置中包含 `meta.validate` 或其它期望返回错误字符串的“旧式校验函数”时
- **那么** 系统不得再依赖该函数执行结构化验证
- **并且** 在开发阶段应通过类型提示或运行时错误向开发者发出明确警告，指引改为使用 Zod Schema
- **并且** 所有新功能与示例必须只展示 Zod 校验用法，不再提供基于 `validate` 的示例或 API 说明

### 需求：灵活的编辑提交模式

系统必须支持三种编辑提交模式，以满足不同的业务场景需求。

#### 场景：即时提交模式（默认）
- **当** `DataGrid` 的 `editMode` 属性为 `'immediate'` 或未设置时
- **那么** 用户编辑单元格后，按下 Enter 键应立即提交到后端
- **并且** 行为与现有实现保持一致，确保向后兼容

#### 场景：单行提交模式
- **当** `DataGrid` 的 `editMode` 属性为 `'single-row'` 时
- **那么** 用户编辑一行中的多个单元格后，编辑内容应暂存在编辑队列中
- **并且** 用户点击该行的"提交"按钮时，才将整行编辑提交到后端
- **并且** 在提交前，必须验证该行的所有编辑内容

#### 场景：批量提交模式
- **当** `DataGrid` 的 `editMode` 属性为 `'batch'` 时
- **那么** 用户编辑多行后，所有编辑内容应暂存在编辑队列中
- **并且** 用户点击"提交全部"按钮时，才将所有待提交的行批量提交到后端
- **并且** 在提交前，必须验证所有待提交的行
- **并且** 如果部分行验证失败，应显示错误信息，但允许提交验证通过的行（可选）

### 需求：编辑队列管理

系统必须维护一个编辑队列，用于暂存待提交的编辑内容。

#### 场景：编辑加入队列
- **当** 用户在非即时提交模式下编辑单元格时
- **那么** 编辑内容应自动加入编辑队列（`pendingEdits`）
- **并且** 如果同一行的同一单元格被多次编辑，应更新队列中的对应记录，而不是创建新记录

#### 场景：从队列移除
- **当** 用户取消编辑或提交成功后
- **那么** 对应的编辑记录应从队列中移除
- **并且** 如果用户点击"取消"按钮，应清空所有待提交的编辑

#### 场景：队列大小限制
- **当** 编辑队列中的记录数超过最大限制（例如 1000 条）时
- **那么** 系统应自动移除最旧的编辑记录
- **并且** 应向用户提示队列已满（可选）

### 需求：提交状态管理

系统必须跟踪提交状态，包括提交中、成功、失败等状态。

#### 场景：提交状态显示
- **当** 用户触发提交操作时
- **那么** 系统应将提交状态设置为 `'submitting'`
- **并且** 在提交过程中，应禁用提交按钮，显示"提交中..."提示
- **并且** 提交成功后，应将状态设置为 `'success'`，并显示成功提示
- **并且** 提交失败后，应将状态设置为 `'error'`，并显示错误信息

#### 场景：部分提交失败处理
- **当** 批量提交时，部分行提交失败
- **那么** 系统应记录失败的行和错误信息
- **并且** 成功提交的行应从队列中移除
- **并且** 失败的行应保留在队列中，允许用户重试

### 需求：性能优化

系统必须在大数据量场景下保持良好的性能表现。

#### 场景：防抖优化
- **当** 用户快速输入编辑内容时
- **那么** 草稿值的更新应使用防抖（例如 150ms）
- **并且** 避免频繁的状态更新导致性能问题

#### 场景：节流优化
- **当** 用户输入过程中需要实时验证时
- **那么** 验证操作应使用节流（例如 300ms）
- **并且** 避免频繁的验证计算导致性能问题

#### 场景：虚拟化优化
- **当** 表格使用虚拟化渲染时
- **那么** 验证操作应只针对可见行的编辑
- **并且** 不可见行的编辑应在滚动到可见区域时再进行验证

### 需求：状态解耦

系统必须将编辑状态与 UI 组件解耦，提升可测试性和可维护性。

#### 场景：状态分层
- **当** 系统管理编辑状态时
- **那么** 应将状态分为三层：
  1. **UI 状态**：当前编辑的单元格、草稿值（在组件中）
  2. **编辑队列**：待提交的编辑记录（在 store 中）
  3. **提交状态**：提交中、成功、失败（在 store 中）

#### 场景：逻辑复用
- **当** 需要在不同组件中使用相同的编辑逻辑时
- **那么** 应通过 Hook（如 `useTableSubmission`）提供可复用的逻辑
- **并且** 编辑逻辑应独立于 UI 组件，易于单元测试

### 需求：行选择模型（Row Selection Model）

系统必须提供统一的行选择状态管理，支持单选和多选模式，并暴露选择状态变更回调。

#### 场景：单选模式
- **当** `DataGrid` 的 `selectionMode` 属性为 `'single'` 时
- **那么** 用户只能选择一行，选择新行时自动取消之前的选择
- **并且** 选择状态存储在 `DataGridRuntimeState.selection` 中（Set<RowKey>）

#### 场景：多选模式（默认）
- **当** `DataGrid` 的 `selectionMode` 属性为 `'multiple'` 或未设置时
- **那么** 用户可以选择多行，点击已选中的行可取消选择
- **并且** 选择状态存储在 `DataGridRuntimeState.selection` 中（Set<RowKey>）

#### 场景：选择状态回调
- **当** 用户选择或取消选择行时
- **那么** 系统必须触发 `onSelectionChange(selectedRowKeys: RowKey[])` 回调
- **并且** 回调参数包含当前所有选中行的 key 数组

#### 场景：受控选择状态
- **当** `DataGrid` 的 `selectedRowKeys` prop 被设置时
- **那么** 表格必须使用该 prop 的值作为选择状态（受控模式）
- **并且** 用户的选择操作必须通过 `onSelectionChange` 回调通知父组件，由父组件更新 `selectedRowKeys`

### 需求：Checkbox 选择列（Selection Checkbox Column）

系统必须在表格最左侧提供固定的 checkbox 列，用于选择行，该列不受列虚拟化影响，始终可见。

#### 场景：显示选择列
- **当** `DataGrid` 的 `enableRowSelection` 属性为 `true`（默认）时
- **那么** 表格必须在最左侧显示一个固定的 checkbox 列
- **并且** 该列必须始终可见，不受列虚拟化、列隐藏、列顺序调整影响

#### 场景：行 checkbox 选择
- **当** 用户点击某行的 checkbox 时
- **那么** 如果该行未选中，则选中该行；如果已选中，则取消选择
- **并且** 选中行的视觉样式必须改变（例如行背景色高亮）
- **并且** checkbox 必须显示勾选状态

#### 场景：表头 checkbox 全选
- **当** 用户点击表头的 checkbox 时
- **那么** 如果当前页有未选中的行，则选中当前页所有行；如果当前页所有行都已选中，则取消选择当前页所有行
- **并且** 表头 checkbox 必须显示正确的状态：
  - 当前页所有行都选中：显示勾选状态
  - 当前页部分行选中：显示半选状态（indeterminate）
  - 当前页没有行选中：显示未勾选状态

#### 场景：选择列宽度
- **当** 选择列渲染时
- **那么** 选择列的宽度必须固定为合理值（例如 48px），不受列宽调整影响
- **并且** 选择列必须位于所有固定列（pinned left）之前

### 需求：范围选择（Range Selection）

系统必须支持通过 Shift + Click 选择连续的行区间。

#### 场景：Shift + Click 范围选择
- **当** 用户按住 Shift 键并点击某行的 checkbox 时
- **那么** 系统必须选择从上次选中的行到当前行的所有行（连续区间）
- **并且** 如果之前没有选中任何行，则仅选择当前行
- **并且** 范围选择必须遵循当前的 `selectionMode`（单选模式下仅选择区间内的第一行）

#### 场景：范围选择跨页
- **当** 用户在当前页选中一行，然后滚动到其他页，按住 Shift 并点击另一行时
- **那么** 系统必须选择从上次选中行到当前行的所有行（包括跨页的行）
- **并且** 如果数据源支持，必须正确选择跨页的行；如果不支持，则仅选择当前页范围内的行

### 需求：选择状态持久化（Selection Persistence）

系统必须支持将选择状态持久化到 localStorage，以便在页面刷新或切换视图后恢复选择状态。

#### 场景：保存选择状态
- **当** `DataGrid` 的 `enableSelectionPersistence` 属性为 `true`（默认）且用户选择或取消选择行时
- **那么** 系统必须将当前选择状态保存到 `localStorage`（key: `grid-${gridId}-selection`）
- **并且** 保存的数据格式必须为 `RowKey[]`（选中行的 key 数组）

#### 场景：恢复选择状态
- **当** `DataGrid` 初始化且 `enableSelectionPersistence` 为 `true` 时
- **那么** 系统必须从 `localStorage` 读取上次保存的选择状态
- **并且** 仅恢复那些在当前数据源中仍然存在的行（通过 `rowKey` 匹配）
- **并且** 如果数据源为空或行 key 不匹配，则忽略持久化的选择状态

#### 场景：清除持久化状态
- **当** 用户点击"清除选择"或所有行都被取消选择时
- **那么** 系统必须清除 `localStorage` 中的选择状态
- **并且** 下次初始化时不会恢复任何选择

### 需求：列头功能集成（Column Header Features Integration）

系统必须在列头提供统一的排序、过滤、分组等功能入口，通过列属性（`ColumnMeta`）控制功能显示，并充分利用现有开源库（TanStack Table、shadcn/ui、Radix UI）实现。

#### 场景：列头操作按钮显示
- **当** `ColumnConfig.meta.enableSorting` 为 `true` 时
- **那么** 列头右侧必须显示排序指示器（↑ ↓ 图标）
- **并且** 点击列头标题或排序指示器可以切换排序状态（升序 → 降序 → 无）

#### 场景：列头过滤按钮显示
- **当** `ColumnConfig.meta.enableFiltering` 为 `true` 时
- **那么** 列头右侧必须显示过滤指示器（过滤图标）
- **并且** 有过滤条件时，过滤指示器必须高亮显示
- **并且** 点击过滤指示器可以打开过滤菜单（Popover）

#### 场景：列头菜单
- **当** 用户点击列头右侧的菜单按钮时

### 需求：增强排序功能（Enhanced Sorting）

#### 场景：单列排序
- **当** 用户点击列头标题或排序指示器时
- **那么** 如果当前未排序，则按升序排序；如果已升序，则按降序排序；如果已降序，则取消排序
- **并且** 排序状态必须通过 `DataGridQuery.sort` 协议推送到数据源
- **并且** 排序状态必须使用 TanStack Table 的 `getSortedRowModel` 进行前端计算（如果数据源支持）

#### 场景：多列排序
- **当** 用户按住 Ctrl（Mac: Cmd）键并点击另一列的排序指示器时
- **那么** 系统必须保留之前的排序，并添加新的排序列
- **并且** 排序优先级按照点击顺序确定（最后点击的列优先级最高）
- **并且** 排序状态必须正确显示在多个列的排序指示器上

#### 场景：排序状态可视化
- **当** 列处于排序状态时
- **那么** 排序指示器必须显示对应的图标（↑ 升序，↓ 降序）
- **并且** 排序指示器必须使用清晰的视觉样式（例如高亮颜色）
- **并且** 多列排序时，每个排序列的指示器必须显示排序序号（1, 2, 3...）

- **并且** 必须创建 `paginationSlice.ts`，管理分页状态（独立管理）

#### 场景：移除 Controller 模式

### 需求：添加分页功能（Add Pagination Feature）

系统必须提供完整的分页功能，支持客户端和服务端两种分页模式，并集成到 DataGrid 组件中。

#### 场景：客户端分页
- **当** 用户启用分页且 `paginationMode` 为 `'client'` 时
- **那么** 系统必须使用 TanStack Table 的 `getPaginationRowModel()` 进行客户端分页
- **并且** 所有数据必须在客户端，分页由 TanStack Table 处理
- **并且** 适合数据量较小（< 10,000 行）的场景

#### 场景：服务端分页
- **当** 用户启用分页且 `paginationMode` 为 `'server'` 时
- **那么** 系统必须使用 `manualPagination: true` 进行服务端分页
- **并且** 必须提供 `rowCount` 或 `pageCount` 参数
- **并且** 分页查询必须通过 `dataSource` 处理

#### 场景：分页 UI 组件
- **当** 用户启用分页时
- **那么** 系统必须显示分页控件，包含首页/上一页/下一页/末页按钮
- **并且** 必须显示页码信息（当前页/总页数）
- **并且** 必须提供每页条数选择器
- **并且** 可选显示总行数

#### 场景：分页状态管理
- **当** 用户切换页码或每页条数时
- **那么** 分页状态必须通过 `paginationSlice` 管理
- **并且** 支持分页状态持久化（可选）
- **并且** 支持 `onPaginationChange` 回调

#### 场景：分页 Props 配置
- **当** 使用 DataGrid 组件时
- **那么** 必须支持 `enablePagination` 属性（默认 false）
- **并且** 必须支持 `paginationMode` 属性（'client' | 'server'，默认 'client'）
- **并且** 必须支持 `initialPageIndex` 和 `initialPageSize` 属性
- **并且** 必须支持 `pageSizeOptions` 属性（默认 [10, 20, 50, 100, 500, 1000, 5000]）
- **并且** 服务端分页时必须支持 `rowCount` 或 `pageCount` 属性
