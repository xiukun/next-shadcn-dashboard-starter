# workspaces 规范

## 目的
本规范定义工作区（workspaces）相关页面在本项目中的职责边界与可验收行为：工作区信息必须通过统一认证上下文获取并展示，避免直接依赖特定认证供应商 SDK；同时规范在“无组织信息/未配置工作区”场景下的引导与降级展示，确保后续接入真实组织管理后端时可平滑替换。
## 需求
### 需求：工作区页面基于统一认证上下文展示组织信息

系统必须确保仪表盘下的“工作区/组织管理”相关页面（例如 `/dashboard/workspaces` 及其子路由）通过统一的认证上下文读取当前组织信息，而不是直接依赖特定认证供应商（如 Clerk）的 Hook 或组件：

- 工作区页面只能通过 `AuthProvider` 暴露的上下文（如 `useAuthContext`）获取当前组织数据。
- 页面展示的组织名称、角色等信息必须来源于由 `auth client` / MSW 返回的会话对象中 `organization` 字段。
- 当不存在组织信息时，页面应提供清晰的引导，引导用户创建或配置工作区，而不是依赖上游 SDK 的默认行为。

#### 场景：已登录且存在组织时展示当前工作区

- **当** 用户已通过 MSW 模式完成登录
- **并且** 当前会话对象中包含 `organization`（含 `name` 与 `role`）
- **当** 用户访问工作区相关页面（例如 `/dashboard/workspaces`）
- **那么** 页面必须通过认证上下文读取当前组织信息
- **并且** 在 UI 中展示该组织名称与角色（例如 “当前工作空间：{organization.name}（角色：{organization.role}）”）

#### 场景：未配置组织时提供创建/配置引导

- **当** 用户已登录但当前会话中不包含任何组织信息
- **当** 用户访问工作区相关页面
- **那么** 页面不得依赖 Clerk 的组织列表/切换能力
- **并且** 必须向用户展示“暂无工作区/请创建或配置工作区”的提示文案或入口
- **并且** 后续接入真实后端时，可以在此位置挂接“创建组织/切换组织”的真实接口或导航，而无需修改现有页面对认证上下文的依赖方式
